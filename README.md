## cgwalters-agentic-job

One reusable workflow is here too:
[cgwalters-agentic-job](.github/workflows/cgwalters-agentic-job.yml), an
agent run of cgwalters-forge/agentic-job with this deployment's tailnet
join, inference proxy, runner, agent and model. Our repositories call it
at main. Any public repository can call it too, and its run's identity
tokens carry the same `job_workflow_ref`, so the inference broker and the
tailnet federation must match `repository_owner_id` against the ids in
[admit/owners.json](admit/owners.json) as well as that `job_workflow_ref`;
both wrappers refuse any other owner before the agent job's runner, which
the caller picks, is given the job ([admit](admit/README.md)). With an
`inference-url` other than ours it needs an `inference-audience` too, so
that our broker's audience is not sent elsewhere by default (the review
wrapper's variables still default apart). It refuses runs
from a private repository, so agentic-job's opt-in for private
repositories, which admits only the calling repository, stays off.

A repository gets agent runs with the workflow below, a bounds file at
`.github/agentic-job/dispatch.toml` (and `fix.toml` for the `fix` kind), a
runner configuration at `.github/agentic-job/hosted.toml`, and an
environment that gates the apply token; cgwalters-forge/tracker has all four
to copy. The file's header says what else a caller may set.

Both wrappers pin agentic-job v0.6.2, by its commit, and check inference
reachability after the tailnet join, before securing the host. They still compose that tag's
`secure-host/internal` action, which runs `sandbox setup` on the host, not
this repository's [secure-host](secure-host/README.md) image action that the
tag's public `secure-host` now forwards to, so its egress
proxy stays a host unit. Since v0.6.0 the agent's home no longer copies the
runner image's `/etc/skel`, toolchains and dotfiles included. The pinned `run` action publishes
the session endpoint itself; no extra endpoint step is needed here.
Mid-run steering stays off unless the caller's runner configuration enables
`[session] watch-item = true`. Policy derives the watched item from the
dispatch wrapper's `issue` (in `output-repo`) or the review event;
`run` needs no additional input. Upstream bounds delivery to 10 updates of
8000 characters, quoted as untrusted item text, not instructions.

```yaml
name: dispatch
run-name: ${{ inputs.kind }} ${{ inputs.repo }}#${{ inputs.item }}
on:
  workflow_dispatch:
    inputs:
      task: {type: string, required: true}
      repo: {type: string, required: true}
      item: {type: string, required: true}
      kind: {type: choice, required: true, options: [implement, triage, research, review, fix]}
permissions: {}
concurrency:
  group: dispatch-${{ inputs.kind }}-${{ inputs.repo }}-${{ inputs.item }}
jobs:
  run:
    uses: cgwalters-forge/actions/.github/workflows/cgwalters-agentic-job.yml@main
    permissions: {contents: read, issues: write, pull-requests: write, actions: read, id-token: write}
    with:
      task: ${{ inputs.task }}
      repo: ${{ inputs.repo }}
      item: ${{ inputs.item }}
      kind: ${{ inputs.kind }}
      apply-environment: agent-apply
    secrets:
      SAFE_OUTPUTS_PAT: ${{ secrets.CGWALTERS_BOT_PAT }}
```

## Review

[cgwalters-review](.github/workflows/cgwalters-review.yml) is the reusable
event-review wrapper. It composes agentic-job **v0.6.2**'s policy, check,
apply and review helpers, so that the tailnet and the inference broker admit
this file's `job_workflow_ref`; agentic-job's review workflow can now run a
caller's own network step instead (its #705), which callers have not moved
to. It refuses private repositories, as the dispatch wrapper does. It adds
our tailnet join and defaults: opencode, the model from
[deployment.json](deployment/README.md), `ubuntu-26.04`, and the dispatch
wrapper's inference URL and audience. It has **no inputs**. Repository/organization variables
`AGENT`, `AGENT_MODEL`, `AGENT_RUNNER` (JSON), `INFERENCE_URL`,
`INFERENCE_AUDIENCE`, `AGENT_CONFIG`, `AGENT_CONFIG_REPO` and
`AGENT_CONFIG_PATH` select owner-controlled configuration. Set the last
two for agents needing external configuration; there is no hard-coded
configuration repository. `AGENT_CONFIG` otherwise uses the pinned
agentic-job hosted configuration. `AGENTIC_JOB_TAILSCALE_OAUTH_CLIENT_ID`
and `AGENTIC_JOB_TAILSCALE_TAGS`, read by both wrappers, are the tailnet
login of an organization that [tailnets.json](tailscale/tailnets.json)
doesn't list; set, they replace a listed organization's entry too. Either
way the wrappers run only for an owner that
[admit/owners.json](admit/owners.json) lists.

Call it from the same `pull_request_target` and `issue_comment` events and
job condition as [this repository's caller](.github/workflows/review.yml),
replacing the job's `uses` with:

```yaml
uses: cgwalters-forge/actions/.github/workflows/cgwalters-review.yml@main
```

Keep that caller's six permission grants. Optional `SAFE_OUTPUTS_PAT` is
forwarded explicitly, only to apply; it never reaches the agent or the real
review submission. Keep `workflow/review.toml`, `workflow/review-command.toml`
and `workflow/review.md` on the caller's base branch. Automatic reviews admit
non-draft owner/member/collaborator PRs, preserving upstream's association
rule for all authors. Otherwise-unassociated bots wait unless `REVIEW_BOT_IDS`
lists their numeric IDs **and** the bounds admit their logins (including
Dependabot). Use a JSON array of numbers; Actions also coerces string IDs.
`/review` still requires write access through event policy.
Only admitted agent jobs enter per-PR concurrency; new automatic events
cancel the old agent, comments do not. The head is data inside the sandbox,
never executed by a privileged step. Each review is bounded to 150 requests,
500 AIC and 75 agent minutes.

`AGENT_REAL_REVIEWS=true` opts into checked APPROVE/REQUEST_CHANGES
submission with the job token, at the admitted head; unset is off. Enable
GitHub Actions' permission to create/approve PRs for this feature. A stale
head, cancellation or failed check cannot produce a new approval. The
compatibility `review` status is not a merge gate or human approval.

For a new repository in this organization, put the review caller and the
three `workflow/review*` files in its **initial commit**, and set the
variables above (copy them from an onboarded repository such as tracker)
and Actions' permission to approve pull requests when you create it. The
organization's ruleset requires an approving review on `main` and has no
bypass actors, but the first push to an empty repository isn't a pull
request, so the review is in place before the first one. Added later, the
onboarding pull request itself needs an approval from an organization
owner, because nothing can review it yet.

A repository whose name ends in `-sandbox` is for agents to iterate in
freely: the organization's approval ruleset excludes it, so its pull
requests merge without a review. When it's ready, renaming it to drop the
suffix brings it under the ruleset; the review above should be in place
before that rename.

Before migrating tracker (a separate repository), admit this wrapper's
`job_workflow_ref`, with the owner ids of admit/owners.json, in the
tailnet federation and inference broker, then
replace its review caller's `uses` as above and exercise a real review and
a synchronize cancellation. No ACL, OAuth or broker policy is changed here;
record those deployment changes in the private wiki when made. Removing the
deployment-specific pieces from agentic-job is a separate follow-up.
`just test-review` checks the wrapper's admission and publication boundaries;
live tailnet joins and GitHub review writes are not exercised locally.

Runs may edit `.github/` here, so pull requests are reviewed by
[this repository's caller](.github/workflows/review.yml) of the wrapper
above, referenced locally so that it runs as on the base branch, never as
a pull request edits it, with this repository's bounds and task in
[workflow/](workflow/review.toml). The ruleset on `main` is to require its
approval, dismissed when new commits are pushed; the approval is submitted
only with the repository variable `AGENT_REAL_REVIEWS=true`, beside the
variables listed above. Dependabot's pull requests are reviewed only with
its ID in `REVIEW_BOT_IDS`. Without `.github/agentic-job/merge.toml` the
reviewer is told a person approves after it.

## Wrapper canary

A pull request that changes either wrapper above is reviewed by the base
branch's copy (the review runs `pull_request_target`), and nothing else
runs an agent through it, so before it merges
[wrapper-canary](.github/workflows/wrapper-canary.yml) runs one real
dispatch and one real review through its copies, in
cgwalters-forge-stage/board-test. The ruleset on `main` is to require the
`wrapper-canary` commit status, which
[wrapper-canary-gate](.github/workflows/wrapper-canary-gate.yml) sets on
every pull request to `main`: success when it changes neither
`cgwalters-agentic-job.yml` nor `cgwalters-review.yml`, pending until a
canary run otherwise, and also when it cannot read every file of that
head (the API lists at most 3,000, and a push can move it). A head brought up to date with `main` is a new
commit, so it needs a new canary run; a pull request with no status
gets one with its next push. The wrappers call `admit`,
`deployment` and `tailscale` at main, so a pull request's copies of those
are not what runs before it merges, and changing them does not ask for a
canary.

The run has the inference identity and the bot's token, so the head is
never run on its own say. A maintainer reads the pull request, pushes the
commit they read to the branch `wrapper-canary` (which works for a fork's
pull request too), and dispatches the canary on main with it:

```sh
SHA=...  # the commit you read, never one fetched after reading
git fetch origin "pull/$PR/head" && test "$(git rev-parse FETCH_HEAD)" = "$SHA"
git push --force origin "$SHA:refs/heads/wrapper-canary"
gh workflow run wrapper-canary.yml --ref main -f pull="$PR" -f sha="$SHA"
```

The push runs that commit's own `push` workflows with this repository's
secrets, so read every workflow change in it, not only the wrappers'. The
canary refuses to start unless the pull request's head, the branch and
`sha` are the same commit. The canary is main's copy, so a pull request
cannot change what decides its status; nor what main's call of the
dispatch wrapper passes and grants, so a pull request that drops an input
that call passes, or gives a job of the wrapper a permission it does not
grant, cannot pass it: change main's call first, in a pull request of its
own.
It calls the dispatch wrapper at `wrapper-canary`, for an
implement run on the scratch issue `WRAPPER_CANARY_ISSUE` within
[canary.toml](.github/agentic-job/canary.toml), told to hand back a noop;
and it reopens the scratch pull request `WRAPPER_CANARY_PULL` with the
bot's token, which starts board-test's `wrapper-canary-review.yml`, a caller
of the review wrapper at `wrapper-canary`. It passes only when each run
called its wrapper at the pull request's head commit (GitHub resolves the
branch when a run starts, and the run records the commit) and succeeded,
its `agent` and `check` jobs included: an agent session started and
handed back a result that check accepted. A healthy run takes a few minutes. The
review gets 12 before the canary fails; the dispatch has only the
wrapper's own limits, so cancel a run that hangs.

Its settings are outside this repository, and in this order, since the
gate leaves wrapper pull requests pending from its merge: board-test's
caller, `.github/workflows/wrapper-canary-review.yml` there, which on
`pull_request_target` `reopened` of the scratch pull request calls the
review wrapper at `@wrapper-canary` from a job keyed `review` with the
six grants of [this repository's caller](.github/workflows/review.yml), the tailnet federation and
inference broker admitting both wrappers' `job_workflow_ref` at
`refs/heads/wrapper-canary` (recorded in the private wiki), the branch
itself at `main` with a ruleset that lets only maintainers update it, as
that admission makes it as trusted as `main`; then the variables
`WRAPPER_CANARY_ISSUE` and `WRAPPER_CANARY_PULL` here, naming a scratch
issue and a non-draft scratch pull request in board-test opened by a
collaborator from a branch there (a fork's would leave the review run
unmatched to it), the `agent-apply` environment and `CGWALTERS_BOT_PAT` as
tracker's dispatch has them; and last the ruleset's required status.

## Lock new items

[lock-new-items](.github/workflows/lock-new-items.yml) locks each newly
opened issue, so that only collaborators can comment on
it and agent runs on it read no outsider's comments (tracker#733). Its one
step locks the item by API with the caller's job token: no PAT, and
nothing of the item is read or run. Pull requests are not locked: a locked
PR refuses reviews from the review job token, and the supervisor only
dispatches issues. It does not cover the opener's own
text, comments in the seconds before the lock, items opened by another
workflow's job token or transferred in (no `opened` event), or items that
predate the caller. A repository opts in with this one
file, `.github/workflows/lock.yml`, as
[this repository's caller](.github/workflows/lock.yml) but for its `uses`:

```yaml
name: lock
on:
  issues:
    types: [opened]
permissions: {}
jobs:
  lock:
    uses: cgwalters-forge/actions/.github/workflows/lock-new-items.yml@main
    permissions:
      issues: write
```

The same pull request exempts the file in
`.github/agentic-job/workflows.toml`, creating it if need be, as this
repository does: without that, workflows-check's shape check refuses every
later pull request. Its zizmor needs the `ref-pin` policy for our own
workflows that [.github/zizmor.yml](.github/zizmor.yml) sets.
